# memory/ —— 记忆与状态层（第 2 步）

长篇连续写作的两个命门：**上下文塞不下** 与 **状态会漂移**。这一层负责这两件事。

## 文件

| 文件 | 作用 |
|---|---|
| `context-budget.js` | `ContextBudget` 上下文预算器（按优先级丢弃）+ `summarizeBible` 设定摘要（打分制 + 每类保底） |
| `state-writer.js` | 状态回写：从正文推导状态变更 + 漂移检测。**编排层强制触发，不靠模型** |
| `drift-rules.js` | 漂移判定规则：区分「正常演化」与「真漂移」 |
| `loop-guard.js` | 把上下文预算接进 Agent 循环，保证 assistant/tool 配对不被破坏 |
| `alias-discovery.js` | 简称发现：找出模型在用、设定库没登记的别名 |
| `test-memory.js` | 46 个验收用例 |
| `test-drift.js` | 19 个漂移用例 |
| `test-loop-guard.js` | 13 个上下文治理用例 |
| `verify-e2e.js` | 端到端：真实模型生成两章 → 落库 → 状态回写 |
| `verify-e2e-context.js` | 端到端：治理开关 A/B 对照（真实模型连写 6 章） |

## 运行

```powershell
# 验收测试（不调模型，秒级）
node memory/test-memory.js
node memory/test-drift.js
node memory/test-loop-guard.js

# 端到端（需 Ollama 在线）
node memory/verify-e2e.js
node memory/verify-e2e-context.js
```

## 三条核心设计

### 1. 压缩不靠模型总结

8B 做摘要会引入二次幻觉——把没读过的写成"读过"。§3.2 已经证明它会凭空编造，
而设定库是最不能出错的地方。**压缩由代码决定裁剪什么，模型只负责它本来就在做的续写。**

丢弃优先级：

1. **未被引用的工具结果** —— 纯噪声，丢了不影响任何后续推理
2. 超出 `keepRecentRounds` 的旧对话轮次
3. 最旧的非 pinned 项

永不丢：`pinned` 条目（system + 设定摘要）、被引用过的工具结果、最近 N 轮。

**关键设计：工具结果按「是否被引用」决定去留，不是按时间。**
一条检索结果被后续 `write_segment` 用到了就留，没用到就丢——
这比按时间裁剪准得多，未使用的老检索结果本来就是噪声。

### 2. 状态回写由编排层强制触发

实测依据：已知实体组 20 个样本，模型 **20/20 只查了 location**；写改组 10/10 只查 character。
**模型按题目需要选实体类型，不会主动维护角色状态。**

所以 `commit_chapter` 之后由编排层扫正文、比对状态表、强制 upsert。这一层是纯代码，
与 §4.2「校验位由代码强制」同一条原则。

### 3. 状态漂移不自动覆盖

新推断的状态与旧状态矛盾时（典型：状态表说在 A 处，正文明确写 B 处），
**报冲突、停下等人裁决，不静默写入**。自动覆盖等于把矛盾当真相。

写入前还做一道**保守的位置判定**：只在「实体名 + 地点动词 + 地点名」三者共现时
才判位置，避免把"他想起铁棺"误判成"他在铁棺"。宁可漏判不可错判。

## 一个实测发现：模型会自造简称

跑真实模型生成 22 章，模型稳定地用「岗北」「岗下」指代设定库里的「乱葬岗」，
但 `world-bible.json` 只登记了别名「岗子」——**没登记「岗北」**。

后果：状态回写判不出「谢九在乱葬岗」，`location` 字段缺失。

这不是 bug 而是设定库的真实缺口：**人写设定时不会穷举所有简称，而模型会自己造。**

`alias-discovery.js` 的策略是保守发现 + 人工确认：

- 只在「方位后缀」这个明确模式下发现（岗北/岗南/城里/冢中…）
- 排除单字、排除与实体名冲突的、排除冗余形态（`乱葬岗下` 与 `岗下` 只留最短）
- **绝不自动写入设定库**，必须显式调 `applyAliasDiscovery`

实测在 22 章落盘稿上发现 2 条：`岗北`、`岗下`。

## 待验

1. **真实长篇的状态漂移率** —— 两章样本零冲突，但 2700 章下漂移是必然的。
   `detectDrift` 只能检出「位置矛盾」，检不出「修为倒退」这类逻辑漂移。
2. **`summarizeBible` 的类型优先级是否合理** —— 当前是 character > technique > faction > plot > location，
   纯按类型判定重要性，未考虑「这个地点在第 300 章还是关键地点」。
3. **上下文压缩的触发时机** —— 现在是调用方主动调 `compress()`，
   实际应接在 Agent 循环里自动触发。
